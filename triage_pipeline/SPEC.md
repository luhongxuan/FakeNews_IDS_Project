# 規格 v0.3：跨平台傳播串分流流程（2026-11-27；使用者已同意位置、分支與開發預設值）

## 0. 設計原則（優先於以下各節）
1. **目標是任何能提供回覆時間與回覆關係的平台**，不是為某一個平台設計。PHEME 與 Bluesky 只是現有的兩份開發資料。
2. **共用程式不得含任何平台名稱或平台專屬分支與數值**。平台差異只能出現在轉接器與由資料決定（第 6.1 節）或使用者依自身需求指定的設定。
3. **不得把任一平台上的實驗結論寫成預設**（例如「某條規則最好」「某訊號最重要」「30 分鐘夠用」）。所有方法在每個平台重新比較。
4. 「適用多平台」須由**設計時完全沒用過的平台**驗證（第 14.1 節）。在此之前只能稱「設計為平台無關，已在兩份開發資料上執行」。

**固定流程，不固定模型。** 每個平台用同一資料格式、特徵、評估與選擇規則，各自訓練。輸出是「此平台建議用哪個排序方法」與依據。
只做**傳播分流**（排出誰之後會有較多回覆），不判斷真假、不估計危害或介入效果。

## 1. 範圍
- **v1 包含**：資料格式、轉接器介面、共用特徵、規則與模型、切分、選擇規則、評估報告。轉接器兩個：Bluesky、PHEME（離線資料）。
- **v1 不包含**：線上蒐集、產品介面與後端整合、查證層、回覆文字特徵、跨平台合併訓練、超參數搜尋、沒有回覆時間或回覆關係的平台。

## 2. 統一資料格式（轉接器唯一要產出的東西）
**threads**：`thread_id`、`created_at`（UTC）、`root_author_id`、`root_text_chars`、`group_id`（評估分組，如日期或事件）、`group_time`（排序用）、`observed_until`（該串回覆蒐集到的時間；不知道填空值）
**replies**：`thread_id`、`reply_id`、`parent_id`（直接回覆原文時等於 `thread_id`）、`author_id`、`offset_sec`（相對原文發布）
- 作者代碼可為雜湊；只用於判斷是否同一人，不輸出。不需要任何貼文文字，只需字數。
- `root_text_chars`＝Unicode 字元數。各平台網址等寫法不同，**此值不可跨平台比較**（本流程不跨平台訓練）。
- 轉接器不得做特徵、篩選或標籤計算。

## 3. 共用清理規則（流程內做，轉接器不做）
| 情況 | 處理 |
|---|---|
| `offset_sec` 缺值或 < 0 | 丟棄該回覆，計數 |
| 重複 `reply_id` | 保留 offset 最小者，計數 |
| 父回覆不存在、已被丟棄，或不在截止點內 | **特徵**中丟棄該回覆及其子回覆（父節點鏈須在截止點內完整），計數 |
| 父回覆時間晚於子回覆 | 依上列規則自然處理；另計數 |
| 循環父子關係、深度無法計算 | 丟棄，計數 |
- 任何特徵只可使用 `0 ≤ offset ≤ T` 的回覆。清理計數寫入報告。
- 目標計數只依時間（不套父節點鏈規則）。
- 平台若沒有巢狀回覆（全部直接回覆原文），深度特徵為常數，流程照常執行並在報告標示。

## 4. 特徵（8 個，定義同既有 Bluesky 研究的 `features_at`）
他人＝作者不同於原文作者。
`n_other`（他人回覆數）、`n_self`（原作者自我回覆數）、`uniq_other`（不重複他人回覆者）、`max_depth`、`mean_depth`（他人回覆；原文直接回覆深度 1；無則 0）、`first_other_s`（首則他人回覆秒數；無則 T）、`n_other_last5`（偏移 > T−300 秒的他人回覆數）、`text_chars`（＝`root_text_chars`）

## 5. 目標與候選母體
- **目標**：偏移在 (T, H] 的**他人**回覆數；模型擬合 log1p。排除自我回覆是因為各平台自我回覆習慣差異大。
- **成熟度**：只有 `observed_until ≥ created_at + H` 的串可作訓練或評估。`observed_until` 未知時報告須標「目標完整性無法驗證」。
- **候選母體**：T 時至少 `min_replies` 則他人回覆（由使用者設定；設 0 表示排全部串）。只用截止點資訊。報告零回覆串占比與它們的之後回覆總量占比（讓使用者知道漏掉多少）。

## 6. 平台設定檔（每個平台一份，**看任何方法表現前固定**）
`T`、`H`、`min_replies`、`top_fraction`、`split_mode`、切分邊界、`group_id` 定義。**沒有跨平台通用的時間預設值**：各平台回覆到達速度可差很多（本專案兩份資料中，最終大小相近的串在 30 分鐘時已到達比例約 72% 對 20%）。
- 使用者依需求指定：`top_fraction`（可處理容量）、`min_replies`（是否需要排零回覆串）、可接受的最晚行動時間 `T_max`。

### 6.1 平台剖析步驟（流程第一步；**只用訓練區段**，不看任何方法表現）
- 輸出：回覆到達曲線、零回覆串占比、各候選 T 的母體覆蓋（候選串數、候選串占全部之後回覆總量的比例、之後回覆仍剩多少）、清理計數。
- **H**：在可完整觀察的追蹤長度候選中（預設格點 24、72、168 小時，平台資料不足時只用可觀察者），取「訓練串在該長度內到達的回覆，占最長可觀察長度總回覆 ≥ 95%」的最小值；皆未達則取最長者並標記「目標可能被截斷」。
- **T**：由使用者在剖析報告的覆蓋資訊上於 `T ≤ T_max` 內選定並寫入設定檔；若未指定，取格點（10、30、60、180 分鐘中不超過 `T_max` 者）裡「候選串在 T 後仍有的回覆，占全部串在 H 內回覆總量」最大的值（同值取較早者）。
- 格點、95% 為判斷值。剖析結果與所選值寫入紀錄；**看過方法表現後不得改 T 或 H**。

## 7. 方法
- **規則**：`U`＝uniq_other；`R1`＝n_other；`R2`＝−(T−最後一則他人回覆偏移)。皆用清理後的他人回覆。
- **模型 M**：RandomForestRegressor，200 棵、max_depth 6、min_samples_leaf 20、種子 20261110–12 平均。v1 不調參。
- **隨機**：解析期望。

## 8. 切分（避免洩漏與高估）
- **`time`（預設，模擬上線）**：依 `group_time` 分成 訓練 → 選擇 → 測試；未另指定邊界時，依組的時間順序取前 60% 組為訓練、接著 20% 為選擇、最後 20% 為測試（組數向下取整，餘數歸訓練）。相鄰區段間須有間隔：前一段每串的 `created_at + H` 早於後一段第一串的 `created_at`，否則丟棄邊界串並計數。
- **`leave_group_out`（事件型離線資料）**：巢狀留一組。外層留一組測試，選擇只用其餘組的內層留一組。報告須標「**非時間前向，不能代表上線表現**」。
- `leave_group_out` 的細節：每個外層折，其餘組做內層留一組，內層各組的指標構成該折的「選擇段」（選擇規則第 10 節套用在其上）；決定採用 M 時，以其餘全部組重訓後評估外層組。第 6.1 節剖析只用該外層折的其餘組。第 10 節的「測試段有效組數 ≥ 3」指**外層折總數**。測試彙總＝各外層折「該折所選方法」的指標平均，另列固定使用各單一方法的平均與每折所選方法次數。
- 測試區段只用一次。不得依測試結果改選擇或設定。

## 9. 指標
- **主要**：每組取分數前 `ceil(top_fraction × 組內候選數)`，抓到的目標總和 ÷ oracle 同額總和；同分取期望值；逐組後平均。目標總和為 0 的組排除並列出。
- **次要**（只報告）：固定前 10 名、組內 Spearman。
- **區間**：原文作者群集配對 bootstrap 2,000 次（種子 42）。

## 10. 選擇規則（只看選擇區段）
1. **資料不足**：訓練候選 < 500 串，或選擇／測試任一段有效組數 < 3 → 不選模型，回報 `insufficient_data`。**不指定任何固定規則為通用預設**：若選擇段至少有 1 個有效組，列出三條規則的點估計並標「僅供暫用、未達選擇門檻」；否則不給建議。
2. 最佳規則＝三條規則中選擇區段主要指標最高者。
3. **採用 M**：M − 最佳規則 的區間下界 > 0 **且**點估計 ≥ +0.02。
4. 否則採用最佳規則。
- 測試區段報告所有方法，但**建議以選擇區段決定的為準**；若測試上所選方法不是最好，照實寫。
- 500、3、0.02 是判斷值，非調校，也未在多平台驗證。

## 11. 需要多少資料（只報告，不參與選擇）
固定選擇與測試區段，訓練只用最接近選擇區段的 1、2、4、7 組與全部組，畫指標與串數。（僅 `time` 模式。）

## 12. 輸出
`recommendation.json` 與一頁 Markdown 報告（所選方法與理由、各方法指標與區間、清理計數、母體覆蓋、限制自動標示）、模型檔（若採用 M，附特徵清單、訓練範圍、設定雜湊）、`run_record.json`；每次新輸出目錄；進度與 `SUCCESS／FAILURE` 加絕對路徑。報告與紀錄不含作者代碼、網址或文字。

## 13. 驗收條件
1. 單元測試（已知答案）：清理規則各情況、截止點邊界（0、T、T+1）、目標邊界（T、H）、成熟度與間隔、特徵、指標同分、選擇規則四條路徑。
2. **洩漏測試**：竄改、刪除、新增截止點後的回覆，特徵、規則分數與候選母體不變。
3. **一致性**：Bluesky 轉接器＋共用特徵，在回覆時間無異常的串上，與既有 `h2.build_frame` 的 8 特徵逐值相同；有差異者逐類列出原因。
4. PHEME 轉接器串數與已知母體一致（七事件謠言 2,298；全部 6,425），自我回覆數與稽核一致。
5. 換平台只新增轉接器與設定檔，不改共用程式（以兩個轉接器證明）。
6. 不連網、不裝套件、不改任何既有檔案與凍結檔案。

## 14. 目前證據與不能宣稱的事
- 已有（探索性，目標含自我回覆、候選定義略不同）：Bluesky 30 分鐘 8 特徵當地模型 0.740、U 0.708、PHEME 部署模型 0.563。
- **未測**：PHEME 用這 8 特徵、本規格的目標與切分；需要多少天資料。
- Bluesky 評估資料已多次使用、PHEME 亦同：兩者在本流程上的結果只能算**驗證流程可執行**，不是對流程選擇能力的獨立確認。
- 兩份資料皆為短文社群平台。**不可宣稱適用所有有回覆串的平台**；論壇、影片留言需另行驗證。

### 14.1 怎樣才能說「不只在某個平台可用」
- **凍結後驗證**：共用程式、格點、門檻與選擇規則凍結並記雜湊後，才取得第三個平台的資料；只新增轉接器與設定檔。
- 第三平台應與短文社群在結構上不同（例如論壇或社群看板、影片留言串），資料須含回覆時間與父子關係，且取得方式符合其使用條款。可用性尚未查證。
- 事先定義成敗：流程能不改共用程式跑完；所選方法在測試段**不顯著遜於**測試段最佳者（差距區間下界容許值於凍結前指定）。
- 即使通過也只能說「在這三個平台上可用」。專案內的 Twitter15/16 與 PHEME 同屬 Twitter，且欄位是否足夠未查證，**不能當作不同類型平台的驗證**。
- 若第三平台失敗並因此修改流程，該平台轉為開發資料，須另找新平台驗證。
